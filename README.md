# PlugManReloaded

Next-Generation менеджер плагинов для серверов Minecraft на базе **Paper 1.16.5+**, **Purpur** и **Folia**. Позволяет загружать, выгружать, включать, выключать и перезагружать плагины без рестарта сервера — с динамическим анализом зависимостей, глубокой очисткой памяти (Metaspace) и защитой сетевого стека.

Команды: `/plugmanreloaded`, `/plugman`, `/plm`.

> Spigot и CraftBukkit не поддерживаются — плагин отклоняет запуск на них при старте.

---

## Совместимость: честно о границах возможного

Выгрузка плагинов «на лету» — это не то, что Bukkit/Paper проектировали как штатную операцию. Сервер отслеживает и умеет корректно снимать только то, что зарегистрировано через его официальный API: слушателей событий, задачи планировщика, сервисы, команды, каналы обмена сообщениями. Всё, что плагин сделал в обход этого — статические кэши, нативные библиотеки через JNI, ссылки, которые взяли другие плагины, — сервер не видит и вернуть не может.

Это не особенность нашей реализации, а свойство архитектуры Java classloading и Bukkit. С этим сталкиваются все менеджеры плагинов, включая оригинальные PlugMan и PlugManX — они точно так же держат список плагинов, которые нельзя трогать. У Paper есть [открытая проблема](https://github.com/PaperMC/Paper/issues/786) с утечкой Metaspace при повторной регистрации слушателей, а разработчик ProtocolLib [прямо заявляет](https://www.spigotmc.org/resources/protocollib-reload-fixer.66860/), что горячая перезагрузка его плагина не поддерживается и поддерживаться не будет.

PlugManReloaded не может это исправить — этого не может никто на уровне плагина. Вместо того чтобы обещать невозможное, он старается **честно предупреждать** и не ломать сервер молча.

### Что не меняет состояние плагинов

`/plm list` и `/plm info` только показывают состояние плагинов.

### Что работает с большинством плагинов

`/plm load`, `/plm enable`, `/plm disable`, `/plm unload`, `/plm reload`, `/plm restart` корректно отрабатывают на обычных плагинах: командных, экономических, игровых механиках, мини-играх, утилитах для администрирования. На современном Paper отключение может закрывать загрузчик классов плагина, поэтому повторное включение загружает новый экземпляр из JAR. При полной выгрузке PlugManReloaded снимает регистрации через официальный API сервера и дополнительно чистит то, что сервер сам не убирает (см. [Как устроена очистка памяти](#как-устроена-очистка-памяти)).

### Что не будет работать никогда — и почему

Некоторые плагины физически не могут быть безопасно выгружены на лету, независимо от того, какой менеджер плагинов используется:

| Категория | Примеры | Почему ломается |
|---|---|---|
| Плагины, встраивающиеся в сетевой стек (Netty) | ProtocolLib, ViaVersion, ViaBackwards, ViaRewind, ProtocolSupport | Патчат Netty-пайплайн сервера при старте. При выгрузке пакетные слушатели других плагинов теряют регистрацию, инжектированные хендлеры остаются висеть. Автор ProtocolLib официально не поддерживает hot-reload. |
| Прокси-протокол/кроссплатформенность | Geyser, Floodgate | Аналогично встраиваются в обработку сетевых пакетов на уровне, недоступном обычному API плагинов. |
| Плагины с нативными библиотеками (JNI) | зависит от сервера | Повторный `System.loadLibrary()` в той же JVM завершается ошибкой `UnsatisfiedLinkError` — JVM не даёт загрузить одну и ту же нативную библиотеку дважды. |
| Плагины с запретом повторной загрузки в JVM | SkinsRestorer | Явно блокируют повторный запуск в той же JVM (`SkinsRestorer was already loaded in this JVM`). |
| Тяжелые плагины с трансформацией байткода | WorldEdit, FastAsyncWorldEdit | Содержат глубокую трансформацию байткода, нативные хуки и тяжелые маппинги, повторная загрузка которых замораживает тиковый поток и приводит к Watchdog crash. |
| Современные Paper-плагины с `PluginBootstrap`/`PluginLoader` | зависит от сервера | Сам Paper не предоставляет API для выгрузки таких плагинов — это ограничение платформы, а не PlugManReloaded. |

Для этой категории плагин по умолчанию **отказывается выгружать без явного подтверждения**. Список настраивается в `config.yml` → `settings.unsafe-to-unload`:

```yaml
settings:
  unsafe-to-unload:
    - "LuckPerms"
    - "Vault"
    - "PlaceholderAPI"
    - "SkinsRestorer"
    - "FastAsyncWorldEdit"
    - "WorldEdit"
    - "ProtocolLib"
    - "ViaVersion"
    - "ViaBackwards"
    - "ViaRewind"
    - "ProtocolSupport"
    - "Geyser-Spigot"
    - "floodgate"
    - "packetevents"
```

Список — не жёсткая зашивка: имена берутся из конфига, можно как убрать, так и добавить свои. Дополнительно плагин детектирует такие библиотеки по наличию их классов внутри `ClassLoader` цели — это работает даже когда список в конфиге не покрывает конкретный форк или переименованную сборку.

### Промежуточный случай: плагины-провайдеры API

Vault, LuckPerms, WorldEdit, PlaceholderAPI и другие плагины, которые сами по себе выгружаются без проблем, но **на них завязаны другие плагины** через `ServicesManager` или прямые ссылки на классы. Выгрузка провайдера при живых зависимых может привести к ошибкам вида `IllegalPluginAccessException` у зависимого плагина (это [известная проблема](https://github.com/LuckPerms/LuckPerms/issues/1691) даже у самого LuckPerms).

PlugManReloaded определяет такие случаи автоматически — через `ServicesManager` и граф зависимостей (`depend`/`softdepend` из `plugin.yml`) — и предлагает каскадную перезагрузку (`-c`), которая перезапускает провайдера вместе со всеми зависимыми в правильном порядке.

Каскадная и массовая операции не выгружают провайдера, если зависимый плагин остался загружен — например, он защищён или его выгрузка завершилась ошибкой.

### Безопасный режим (`safe-mode`)

Включён по умолчанию. При попытке выгрузить рискованный плагин (из списка `unsafe-to-unload`, перехватывающий сетевой стек, являющийся провайдером API, или имеющий зависимые плагины) команда не выполняется молча, а показывает предупреждение с причиной риска и просит подтверждения — либо кнопкой в чате, либо флагом `-y`:

```
/plm unload ProtocolLib
> ⚠ Плагин ProtocolLib встраивается в сетевой стек сервера при запуске
> и корректно выгрузиться не может. Нужен перезапуск сервера!
> [Выгрузить всё равно]   [Отменить]
```

Отключить проверку для конкретной команды: `/plm unload <плагин> -y`. Отключить полностью: `settings.safe-mode.enabled: false` в `config.yml` (не рекомендуется).

### Совместимость по версиям

| Компонент | Поддерживаемая версия |
|---|---|
| Minecraft / Paper API | 1.16.5 и новее (`api-version: 1.16`) |
| Java | 16+ |
| Ядра | Paper, Purpur, Folia |
| Не поддерживается | Spigot, CraftBukkit (плагин отклоняет запуск при старте) |

Плагин определяет платформу в рантайме и адаптирует поведение: на современном Paper (1.19.3+) используется актуальный `PaperPluginManagerImpl`, на более старых версиях — легаси-путь через `SimplePluginManager`. Внутренние структуры сервера, к которым обращается плагин (реестры плагинов, дерево зависимостей), могут меняться между версиями Paper без предупреждения — при обновлении сервера на новую мажорную версию Paper стоит проверить работу критичных команд перед использованием в проде.

На Folia при выключении плагина отменяются его задачи глобального и асинхронного планировщиков. У `EntityScheduler` нет общего метода отмены задач по плагину: отложенные задачи сущностей могут удерживать ссылки на его классы до завершения задачи или удаления сущности. Плагины, которые планируют такие задачи на длительное время, лучше обновлять с перезапуском сервера.

## Как устроена очистка памяти

При полной выгрузке (`unload`, `restart`, каскадной и массовой перезагрузке; на Modern Paper — также при обычном `reload`) плагин выполняет то, что сервер не делает сам:

- разрегистрирует сервисы, слушателей событий, задачи планировщика, каналы сообщений (через официальный Bukkit API);
- снимает хуки PlaceholderAPI, ProtocolLib, PacketEvents — если они установлены и включены;
- очищает Netty-пайплайны игроков от инжектированных хендлеров выгружаемого плагина;
- закрывает открытые GUI-инвентари и снимает `PermissionAttachment`, оставленные плагином у игроков;
- прерывает фоновые потоки, привязанные к `ClassLoader` плагина;
- дерегистрирует JDBC-драйверы, зарегистрированные плагином;
- сбрасывает кэш `java.beans.Introspector` и внутренние кэши Paper-загрузчика;
- закрывает `ClassLoader` плагина.

Ни один из этих шагов не гарантирует стопроцентного освобождения памяти — см. раздел про совместимость выше. Но это максимум, что можно сделать, оставаясь плагином, а не патчем сервера.

## Обновление плагинов

Команда `/plm update` находит новые версии установленных плагинов и, где это возможно, устанавливает их.

```
/plm update                    проверить все плагины (ничего не скачивает)
/plm update <плагин>           проверить один, показать кнопку установки
/plm update <плагин> -y        установить сразу
/plm update all -y             обновить всё, что прошло строгие критерии
```

**Проверка по умолчанию ничего не качает** — команду без флагов можно безопасно давать модератору.

### Как плагин опознаётся

Сначала считается SHA1 установленного `.jar` и одним запросом отправляется на Modrinth. Если хеш найден — проект и версия определены **точно**, без догадок по названию. Такое совпадение помечается как подтверждённое и только оно может устанавливаться массово.

Если хеша нет в базе, используется каталог известных плагинов (по главному классу из `plugin.yml`) и поиск по имени. Такие совпадения требуют подтверждения кнопкой — установить их можно, но только вручную.

### Источники и их возможности

| Источник | Совместимость с версией MC | Канал (alpha/beta) | Установка |
|---|---|---|---|
| Modrinth | ✅ точно, по каждой версии | ✅ | автоматическая |
| Hangar | ✅ точно, по каждой версии | ✅ | автоматическая |
| GitHub | ❌ не сообщается | ⚠️ только пометка pre-release | с подтверждением |
| SpigotMC | ❌ не сообщается | ❌ | только уведомление |
| Ruspigot (spigotmc.ru) | ❌ не сообщается | ❌ | с подтверждением, если на странице ресурса указано поле «Исходный код» |
| Сайт вендора | ❌ не сообщается | ✅ релиз | с подтверждением |
| Jenkins CI | ❌ не сообщается | сборки = alpha | с подтверждением |

Отдельно про **Ruspigot**: плагины там скачать без авторизации нельзя, но плагин читает поле «Исходный код» на странице ресурса — если автор указал там GitHub-репозиторий, обновления будут искаться в релизах этого репозитория и предложены кнопкой с подтверждением. Без такого поля остаётся честное уведомление со ссылкой на ресурс.

### Платные плагины

Платные ресурсы распознаются на SpigotMC (метка premium в API) и на Ruspigot (метка «Платно»). Для них плагин показывает отдельное сообщение: какая версия вышла и ссылка на страницу покупки — кнопки установки не будет. Бесплатную версию вместо платной плагин не подставляет: если у одного плагина существуют платная и бесплатная версии, при равном номере версии приоритет отдан платному кандидату, чтобы обновление случайно не заменило купленную сборку урезанной бесплатной. Бесплатная версия предлагается только если она реально свежее платной.

Некоторые плагины раздаются мимо площадок — с собственного сайта или сборочного сервера, и такой источник нередко **свежее Modrinth**: у LuckPerms на официальном сайте 5.5.77 против 5.5.71 на Modrinth.

Встроенный каталог содержит только плагины, которые **нельзя найти автоматически** — те, что не выложены ни на Modrinth, ни на Hangar, ни на SpigotMC (каждая запись проверяется API-запросами ко всем трём площадкам). Сейчас это:

| Плагин | Откуда берётся |
|---|---|
| LuckPerms | сайт вендора (`metadata.luckperms.net`, свежее Modrinth) + свой Jenkins |
| Модули EssentialsX (Chat, Spawn, Protect, AntiBuild, Discord, GeoIP и другие) | GitHub-релизы EssentialsX + `ci.ender.zone` |

Модули EssentialsX — самый показательный случай: на Modrinth лежит только основной jar, а модули существуют лишь в релизах GitHub и на Jenkins.

Сборочный сервер отдаёт именно **сборки, а не релизы**, поэтому они помечаются как alpha и никогда не ставятся без подтверждения. Такие источники используются последними — если плагин нашёлся на Modrinth или Hangar, берётся оттуда.

Когда вендор публикует несколько сборок под разные платформы (у AuthMe обычного jar нет вообще — только `-Paper`, `-Spigot`, `-Folia`, `-Bungee`), выбирается сборка под Paper. Файлы вроде `-javadoc`, `-sources` и сборки под чужие платформы отсеиваются до сравнения.

Сайты без машинночитаемого эндпоинта не поддерживаются: разбор чужой вёрстки ломается при первом же редизайне. Для них плагин честно даёт ссылку на страницу загрузки.


### Свои источники

Встроенный список небольшой и содержит только проверенные записи — угнаться за всеми плагинами
нельзя, да и не нужно. Всё остальное добавляется в файл `plugins/PlugManReloaded/sources-custom.yml`,
который создаётся при первом запуске:

```yaml
plugins:
  МойПлагин:
    sources:
      - id: github
        ref: "MyName/MyPlugin"
```

Ключ записи — имя плагина так, как его показывает `/plm list`. Записи из этого файла имеют приоритет
над встроенными, поэтому им же можно исправить неправильно определённый плагин.

Необязательное поле `main` привязывает запись к конкретному главному классу — это нужно форкам,
которые наследуют главный класс оригинала. Без такой привязки форк вроде `VaultSlim` подхватил бы
ссылки обычного Vault и заменил бы себя им.

После правки файла — `/plm config reload`. Формат подробно расписан комментариями внутри самого файла.

Также источник можно указать прямо в чате: если при выполнении `/plm update <плагин>` источник не найден, плагин предложит нажать кнопку **«[Указать источник]»**. После нажатия администратор может отправить в чат ссылку на страницу проекта (GitHub, Modrinth, Hangar, SpigotMC, Jenkins). Плагин автоматически распознает ссылку, проверит наличие релизов и сохранит запись в `sources-custom.yml`.

SpigotMC не отдаёт ни совместимости с версией сервера, ни контрольных сумм, ни ссылки на конкретную версию — оттуда плагин только сообщит, что вышло обновление, и даст ссылку для ручной установки. То же касается платных и внешних ресурсов.

### Что происходит при установке

1. Файл скачивается во временную папку.
2. Сверяется контрольная сумма (SHA1 или SHA256, смотря что даёт источник).
3. Открывается архив и проверяется, что имя плагина внутри совпадает с обновляемым.
4. Старая версия копируется в `plugins/.plugmanreloaded-backups/`.
5. Плагин выгружается, файл заменяется, плагин загружается снова.
6. Если новая версия не запустилась — автоматический откат к прежней.

Рабочий `.jar` удаляется только после того, как новый скачан и проверен. Если старый файл не удалось удалить (обычно из-за блокировки на Windows), обновление откатывается целиком — иначе в `plugins/` оказались бы две копии одного плагина.

Плагины, которые встраиваются в сетевой стек (`ProtocolLib`, `ViaVersion` и прочие из `unsafe-to-unload`), **не выгружаются на лету вообще**. Для них проверенный файл кладётся в штатную папку отложенных обновлений сервера, и Minecraft применит его сам при следующем запуске. Плагин при этом продолжает работать в прежней версии, ничего не ломается.

### Настройки

```yaml
settings:
  updates:
    check-on-start: true      # проверять при старте сервера
    allow-prerelease: false   # предлагать alpha и beta версии
    github-token: ""          # без токена лимит GitHub — 60 запросов в час
    cache-ttl-hours: 6
    manual-source:
      enabled: true           # разрешить указание источника через чат
      timeout-seconds: 60     # время ожидания ввода ссылки
  backups:
    keep-days: 1              # сколько дней хранить бэкапы (старше удаляются)
    max-backups-per-plugin: 3 # максимум копий для каждого плагина
  delete:
    delete-data-folder: false # удалять ли папку данных плагина при /plm delete
```

## Скачивание плагинов

Команда `/plm download` позволяет искать и скачивать плагины с Modrinth, Hangar, SpigotMC и GitHub с автоматическим определением зависимостей и совместимости.

```
/plm download <URL>                  скачать плагин по ссылке на страницу проекта
/plm download <название>             найти плагин и показать интерактивные карточки
/plm download <название> -y          скачать плагин с авто-подтверждением зависимостей
/plm download <название> -s modrinth искать только на конкретной площадке (modrinth/hangar/spigot/github)
/plm download <название> -w          также скачивать необязательные зависимости (-w или --with-soft-deps)
```

Прямые ссылки на `.jar` не принимаются: укажите страницу проекта на поддерживаемой площадке

### Как устроена установка и безопасность

1. **Многокритериальный скоринг и поиск:** ранжирует результаты по точности имени, официальному каталогу, совместимости с версией Minecraft/Paper сервера и популярности, отсекая аддоны и чужие форки.
2. **Анализ зависимостей (DAG):** сканирует `depend`, `softdepend` и `paper-plugin.yml`. Проверяет наличие плагинов на сервере (включая виртуальные алиасы `provides:`). Если обязательных зависимостей не хватает — предлагает скачать их одной кнопкой в чате.
3. **Двухфазная транзакция (2PC):**
   - Скачивание всех файлов во временную изолированную директорию.
   - Валидация Magic Bytes (`PK\003\004`), контрольных сумм SHA-512/SHA-256, дескрипторов и целевой версии Java (`CA FE BA BE`).
   - Атомарный перенос в `plugins/` (с поддержкой отложенной загрузки через `plugins/update/` при Paper Bootstrapper или блокировках Windows).
   - Активация в топологическом порядке. При сбое на этапе активации — автоматический откат (санация и удаление добавленных файлов).
4. **Автоматическое запоминание источника:** после успешной установки источник плагина записывается в `sources-custom.yml`, чтобы `/plm update` мог регулярно проверять новые версии.

## Конфигурация

Поведение плагина настраивается в `config.yml`, а тексты — в отдельных файлах (см. [Языки и локализация](#языки-и-локализация)). Ключевые опции:

- `settings.safe-mode.enabled` — включает подтверждение для рискованных операций (по умолчанию `true`).
- `settings.unsafe-to-unload` — список плагинов, требующих подтверждения при выгрузке.
- `settings.ignored-plugins` — список плагинов, которые вообще нельзя трогать командами плагина.
- `settings.cascade-reload.by-default` — каскадная перезагрузка по умолчанию без флага `-c`.
- `settings.hot-swap.enabled` — автоматическая перезагрузка плагина при замене его `.jar`-файла в папке `plugins/`.
- `settings.download.suggestions.enabled` — показ подсказок популярных плагинов в автодополнении `/plm download` (`hide-downloaded` скрывает уже скачанные).
- `settings.backups.keep-days` — срок хранения резервных копий в днях.
- `settings.delete.delete-data-folder` — удаление папки с конфигурацией при `/plm delete`.

При обновлении плагина новые ключи конфига добавляются автоматически при сохранении пользовательских значений (`ConfigUpdater`), версия отслеживается через `config-version`.

## Языки и локализация

Плагин полностью двуязычный: русский и английский. Язык выбирается одним параметром:

```yaml
settings:
  language: ru   # ru или en
```

После смены языка достаточно `/plm config reload` — перезапуск сервера не нужен. Переключаются **все три** слоя сразу:

| Слой | Где лежит | Что это |
|---|---|---|
| Сообщения игрокам | `messages/ru-messages.yml`, `messages/en-messages.yml` | Весь вывод команд: тексты, цвета, звуки, кнопки, ховеры |
| Логи консоли | `messages/logs/ru-logs.yml`, `messages/logs/en-logs.yml` | Служебный вывод для владельца сервера, включая `debug`-диагностику |
| Комментарии `config.yml` | внутри `.jar` | Пояснения к параметрам переписываются на выбранный язык прямо в файле |

Про комментарии подробнее: при смене языка плагин **перерисовывает `config.yml`**, подставляя пояснения на нужном языке, а все ваши значения оставляет ровно такими, какими вы их выставили. Перед записью делается резервная копия в `backups/configs/`, и если хоть один параметр не пережил бы перерисовку — правка отменяется целиком, а в консоль уходит предупреждение. В папке плагина при этом всегда лежит **один** `config.yml`, а не по файлу на язык.

Все файлы текстов можно свободно редактировать — при обновлении плагина недостающие ключи дольются автоматически, ваши правки сохранятся. Если указать язык, для которого файлов нет (например, `language: de`), плагин возьмёт русский как запасной и **не тронет** ваш `config.yml`.

## Developer API

**PlugManReloaded** предоставляет современный, типобезопасный API для программного управления плагинами, графом зависимостей и событиями жизненного цикла.

Добавьте `PlugManReloaded` в `depend` (или `softdepend`) своего `plugin.yml`, прежде чем звать `PlugManAPI.get()` — метод бросает `IllegalStateException`, если плагин ещё не загружен/не включён.

**Потокобезопасность.** Любую операцию можно звать из любого потока. Если вызов пришёл не с главного потока сервера, реализация сама перекладывает операцию на главный поток и блокирует вызывающий поток до её завершения (либо до 30 секунд — после этого возвращается неуспешный `PluginResult`, а не зависание навсегда).

### Подключение в проект (Maven)

```xml
<dependency>
    <groupId>ru.milkyway</groupId>
    <artifactId>PlugManReloaded</artifactId>
    <version>1.0</version>
    <scope>provided</scope>
</dependency>
```

### 1. Быстрый статический фасад

```java
import ru.milkyway.plugmanreloaded.api.PlugManAPI;
import ru.milkyway.plugmanreloaded.api.PluginResult;
import ru.milkyway.plugmanreloaded.api.PluginInfo;

// Перезагрузка любого плагина в одну строку
PluginResult result = PlugManAPI.reload("DecentHolograms");
if (result.isSuccess()) {
    long elapsed = result.getElapsedMs();
}
// ВАЖНО: result.messageKey() — это внутренний ключ каталога сообщений (например
// "errors.plugin-not-found"), а НЕ готовый текст для игрока. Показывать его напрямую нельзя —
// это тот же ключ, которым команды плагина рендерят свои локализованные цветные сообщения.
// Если нужен именно текст — либо ветвитесь по messageKey() сами, либо возьмите
// result.placeholders() (значения, которые PlugManReloaded подставил бы в этот ключ) и
// отрендерите сообщение своими средствами.

// Загрузка, выгрузка, включение, выключение
PlugManAPI.load("MyPlugin.jar");
PlugManAPI.unload("MyPlugin");
PlugManAPI.enable("MyPlugin");
PlugManAPI.disable("MyPlugin");

// Получение информации о плагине
Optional<PluginInfo> info = PlugManAPI.getInfo("LuckPerms");
info.ifPresent(i -> {
    String version = i.version();
    long size = i.fileSizeBytes();
});
```

### 2. Модульные сервисы подсистем

```java
PlugManAPI api = PlugManAPI.get();

// Жизненный цикл плагинов
PluginLifecycleService lifecycle = api.lifecycle();

// unloadPlugin(plugin, deep): deep=false — операция ОТКАЖЕТ (ключ "errors.has-dependents"),
// если у плагина есть загруженные зависимые, вместо того чтобы молча оставить их висеть на
// выгруженном classloader'е. deep=true — безусловно, как обычный /plm unload.
lifecycle.unloadPlugin("SomeApiProviderPlugin", false);

// Анализ графа зависимостей (DAG)
DependencyGraphService graph = api.graph();
Set<String> dependents = graph.getDependents("Vault");
List<String> cascadeOrder = graph.getCascadeUnloadOrder("Vault");

// Реестр плагинов и файлов
PluginRegistryService registry = api.registry();
// getLoadablePluginNames() — это НЕ "все плагины", а только те, что СЕЙЧАС НЕ загружены, но
// лежат .jar-файлом в папке плагинов (ровно то, что предложит /plm load). Для полного списка
// загруженных плагинов используйте registry.getAllPlugins().
List<String> loadable = registry.getLoadablePluginNames();

// Асинхронная проверка обновлений. Сетевые запросы идут в фоновом потоке, но переданный сюда
// callback гарантированно выполнится на ГЛАВНОМ потоке сервера — трогать Bukkit API внутри
// thenAccept/thenRun можно без дополнительного переключения потоков.
UpdateServiceAPI updates = api.updates();
updates.checkUpdate("EssentialsX").thenAccept(opt -> {
    opt.ifPresent(u -> {
        if (u.hasUpdate()) {
            // u.newVersion(), u.sourceUrl(), u.downloadable()
        }
    });
});

// Служба Hot-Swap
HotSwapService hotswap = api.hotswap();
boolean running = hotswap.isEnabled();
```

### 3. События жизненного цикла (Bukkit Events)

Вы можете отслеживать или программно отменять операции с плагинами:

| Событие | Cancellable | Описание |
|---|:---:|---|
| `PluginPreLoadEvent` | ✅ | Перед загрузкой `.jar` (`/plm load` или API) — уже ПОСЛЕ собственных pre-flight проверок PlugManReloaded (валидность jar, версия Java, дубликаты имён), так что можно добавить свою финальную проверку, не дублируя чужие |
| `PluginLoadedEvent` | ❌ | После успешной загрузки и включения плагина |
| `PluginPreUnloadEvent` | ✅ | Перед выгрузкой через `/plm unload` или API `unloadPlugin`. Обычные `/plm reload` и `/plm restart` шлют `PluginPreReloadEvent` |
| `PluginUnloadedEvent` | ❌ | После завершения выгрузки. К этому моменту классы плагина уже выгружены, поэтому событие несёт имя плагина строкой, а не `Plugin` |
| `PluginPreReloadEvent` | ✅ | Перед перезагрузкой или полным перезапуском плагина |
| `PluginReloadedEvent` | ❌ | После успешной перезагрузки/перезапуска (содержит время в мс) |
| `PluginUpdateFoundEvent` | ❌ | Найдена более новая версия установленного плагина — при автопроверке на старте сервера (если включена `settings.updates.check-on-start`) либо при ручном `/plm update`. Отдельного периодического таймера для чужих плагинов нет (только для самопроверки PlugManReloaded) |

`PluginPreUnloadEvent`/`PluginUnloadedEvent` несут флаг `isDeep()` — то самое значение `deep`, что передали в `PluginLifecycleService.unloadPlugin(plugin, deep)` (см. пример выше).

**Пример слушателя событий:**
```java
@EventHandler
public void onPreUnload(PluginPreUnloadEvent event) {
    if (event.getPluginName().equalsIgnoreCase("CriticalSecurityPlugin")) {
        event.setCancelled(true); // Запретить выгрузку плагина
    }
}

@EventHandler
public void onReloaded(PluginReloadedEvent event) {
    getLogger().info("Плагин " + event.getPluginName() + " перезагружен за " + event.getElapsedMs() + " мс");
}
```

### 4. Справочник типов данных

**`PluginResult`** — результат операции жизненного цикла (load/unload/reload/restart/enable/disable/delete).

| Поле | Что содержит |
|---|---|
| `success` | успешна ли операция |
| `messageKey` | внутренний ключ каталога сообщений (**не готовый текст**, см. предупреждение выше) |
| `placeholders` | значения, которые подставились бы в этот ключ (например `{"plugin": "Vault"}`) |
| `error` | исключение, вызвавшее ошибку, либо `null` |
| `elapsedMs` | сколько заняла операция в миллисекундах, либо `0`, если не измерялось |

**`PluginInfo`** — снимок метаданных плагина, из `plugin.yml`/`paper-plugin.yml`. Работает и для загруженных плагинов (`PluginInfo.fromPlugin`), и для плагинов, лежащих только `.jar`-файлом на диске (`PluginInfo.fromJarFile`) — для вторых `enabled()` всегда `false`, а `commands()`/`permissions()` всегда пустые (это недоступно без загрузки плагина). Поля: `name`, `version`, `mainClass`, `authors`, `description`, `website`, `depends`, `softDepends`, `commands`, `permissions`, `file`, `fileSizeBytes`, `enabled`, `isPaperPlugin`, `hasBootstrapper`. Метод `fileSizeFormatted()` отдаёт `fileSizeBytes` в человекочитаемом виде («1.44 MB»).

**`UpdateInfo`** — результат сопоставления плагина с источниками обновлений (GitHub, Modrinth, Hangar, SpigotMC…).

| Поле | Что содержит |
|---|---|
| `pluginName` | имя плагина |
| `currentVersion` | установленная версия |
| `newVersion` | версия, найденная на источнике |
| `sourceId` | id источника (`"github"`, `"modrinth"`…), либо `"none"`, если источник не найден |
| `sourceUrl` | прямая ссылка на скачивание `newVersion`, либо пустая строка |
| `downloadable` | может ли PlugManReloaded скачать и установить `newVersion` автоматически |
| `isPremium` | платный/премиум ли источник (такие никогда не скачиваются автоматически) |
| `hasUpdate` | действительно ли `newVersion` новее `currentVersion` |

**`DependencyNode`** — место одного плагина в графе зависимостей. `getHardDependencies()` — обязательные (`depend`), `getSoftDependencies()` — опциональные (`softdepend`), `getDependents()` — кто зависит от ЭТОГО плагина. Объект неизменяемый (мутабелен только во время построения графа внутри самого PlugManReloaded).

**`BulkOperationResult`** — результат массовой операции (`/plm reload -all` и аналоги). Поля: `total` (сколько плагинов затронуто), `successCount`, `successfulPlugins`, `failedPlugins`, `failureReasons` (короткая причина на каждый провалившийся плагин), `elapsedMillis`. Методы-хелперы: `isAllSuccessful()`, `isEmpty()` (ничего не затронуто), `failedCount()`.

**`PlugManProvider`** — статический холдер активного `PlugManAPI`-инстанса; сторонним плагинам стоит звать `PlugManAPI.get()`, а не эту точку напрямую. `register`/`unregister` вызываются самим PlugManReloaded в `onEnable`/`onDisable` и не предназначены для сторонних плагинов.
